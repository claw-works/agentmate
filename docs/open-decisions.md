# 已定决策

原先这里收的是"需要产品/所有者输入"的 9 条待决项。2026-08-01 授权由我决定，本文档
因此从待办清单变成决策记录：每条给出**结论、理由、落地位置**，以及**推翻它需要什么**。

只有一条没有结论：第 4 条的具体单价。理由在那一节里说明——它不是判断问题。

---

## 1. 编译触发时机：保持显式触发，但让"过旧"变响

**结论**：不做"sync 后自动编译"。保持 `POST /api/knowledge/compile` 显式触发。

**理由**：自动编译把两个不同主体的意图绑在了一起。推 raw source 的人是在改事实源，
不一定在那个时刻想重建 wiki、也不一定想付这次模型账单；而一次 typo 修正连推五次，
就是五次编译。更根本的是，编译是**不可重现且花钱**的操作，把它做成 git push 的副作用
意味着没有任何人**决定**过这次重建。

**但"静默变旧"这个代价必须消除**，而消除它的正确手段不是自动编译，是可见性：
K3.7 的 `stale_citation` 已经能报出"页引用的源文档变了或没了"，这是确定性的、不花钱的。
把钱花在编译上来避免变旧，和把 lint 结果读一遍来发现变旧，后者便宜几个数量级。

**推翻它需要什么**：一个愿意为"知识库始终最新"付固定账单的场景（例如对外 SLA），
且那时应该做的是**带冷却窗口的增量编译**，而不是每次 sync 都全量编。

## 2. build 保留窗口：暂不淘汰，淘汰时的下限已定

**结论**：现在全部保留。将来引入淘汰策略时，下限是**同时**满足：

- 保留期 ≥ 90 天；
- 永远保留当前 active build 及其 parent 链（增量编译的 parent 缺失会使该链无法解释）。

**理由**：淘汰窗口不能短于 validation 信号的显形周期（K3 §7.3：问题可能几周后才发现），
否则会在发现问题的那一刻恰好失去可回滚的目标。90 天 ≈ 13 周，覆盖"几周"的上界。
当前量级是个位数 build，现在写淘汰逻辑属于给不存在的问题写代码。

**推翻它需要什么**：build 表的体积成为真实成本项。届时按上面的下限实现，不要因为
"清理起来简单"而按数量（例如"只留最近 10 个"）淘汰——数量与信号周期无关。

## 3. proposal 的处置人：账户所有者，且过期即处置

**结论**：不引入独立的审批角色。proposal 是**寄给账户所有者的报告**，不是等人签字的队列：

- 处置权属于知识源所属账户本身；单租户即单账户的产品形态下，再造一个"审批人"角色
  是凭空发明一个客户没有的流程；
- **未处置的 proposal 在 30 天后过期，并把过期本身记为一次处置**（带理由：无人处置）。

**理由**：原来的疑问"由谁批"预设了 proposal 需要被批准才能**变成什么东西**。但架构
§0.2 已经定了 proposal 不是 mutation——它是一个发现，本身就已经完成了它的全部作用。
所以真正要防的不是"没人批"，而是文档自己警告过的那件事：**一个只进不出的队列**，
它会让人误以为反馈已经被处理了。过期并记录，队列就会排空，而"没人管"变成一条可以
被统计的事实，而不是一堆越积越多的未读。

**推翻它需要什么**：多人协作的账户，且 proposal 会触发花钱的动作（比如自动重编译）。
那时需要的是"谁被通知"，仍然不是"谁有权批准"。

## 4. 两家 provider 的单价：策略已定，数字仍缺

**这一条没有结论，且不可能由我给出结论**：单价是你和阿里云、DeepSeek 的合同价格。
它不是判断问题，是一个我没有的输入。编一个"看起来合理"的数字，就是在成本表上放一个
看起来权威的错数字——这正是 `llm.Pricing` 默认 0、拒绝编造默认值的原因。

**我定的是它的呈现方式**：`cost_micros: 0` 现在能和"这次编译真的没花钱"区分开。
判定不需要新列——任何被配置过的单价乘以非零 token 必然大于 0，所以"花了 token 却记成
0 成本"唯一的解释就是没配单价。build 响应新增派生字段：

- `cost_priced: false` → 单价未配置，这个 0 不是"免费"；
- `review_cost_priced` 同理。

**落地**：`internal/knowledge/wiki_model.go` 的 `BuildRevision.MarshalJSON`
（放在序列化唯一出口，避免漏改某个 scan 点导致各读路径答案分叉）。

**你要填的**：`COMPILER_INPUT_MICROS_PER_1K_TOKENS`、
`COMPILER_OUTPUT_MICROS_PER_1K_TOKENS`，以及对应的 `REVIEWER_*`。填上之后
"增量编译省了多少钱"才能用金额回答，现在只能用 token 数回答。

## 5. memory entry 的 title：读侧派生，不强制写入方

**结论**：不要求写入方必填 `title`。缺失时在读侧派生显示标签。

**理由**：被强制填 title 的 agent 会产出"关于 X 的记忆"这类没有信息量的标题——把工作
推给写入侧只会换来噪音，而且要求必填会让老数据全部不合规。"显示成什么"本来就是读侧
的问题，就在读侧解决。

派生规则确定性、无模型调用：`title` → `summary` 首行 → 正文首行，去掉 Markdown 标记
后按 rune 截断到 80。三者都空时**只显示 `memory_type`，不编标题**——空标题的含义是
"这条没写标题"，编出来的标题含义是"这条的标题是假的"。前缀始终带 `memory_type`，
因为读者需要知道这是事实（semantic）、经历（episodic）还是方法（procedural）：
三者的可信方式不同，显示成同一种东西会让 agent 用错。

**落地**：`internal/contextpack/service.go` 的 `memoryLabel`。

## 6. 三张表的 `account_id`：改为 CASCADE

**结论**：`api_logs`、`retrieval_queries`、`retrieval_feedback` 从 `SET NULL`
改为 `ON DELETE CASCADE`。

**理由**：三张表都存客户内容——`retrieval_queries` 存查询原文（用户问了什么），
`retrieval_feedback` 存对结果的判断，`api_logs` 存请求元数据。`SET NULL` 之后这些行
留在库里、失去归属，于是"账户已删除"和"这个人问过什么"同时成立：删除承诺没有兑现，
而且再也无法按账户找回来删。

先例已经立好：migration `000025` 当初把 `skill_versions`、`skill_logs` 从 `SET NULL`
改成 `CASCADE`，理由一模一样。这三张表是当时漏掉的同一类。

反方论点"保留数据做聚合分析"不成立：聚合不需要可识别的行。要指标就预聚合成不带
`account_id` 的计数，而不是留一堆无主明细等着以后"也许有用"。

**落地**：migration `000036`。已存在的孤立行不动——它们诞生在这次改动之前，已无法
归属到任何账户，静默删掉无法归属的客户数据比留着更糟（留着至少是可清点的）。
清点：`SELECT count(*) FROM retrieval_queries WHERE account_id IS NULL;`

## 7 / 8. 编译器不织网、且写入无据断言：改 prompt，不进 check，不为验证付费

这两条是同一个决定的两面（都要重编译才能验证），所以一起定。

**结论**：改编译 prompt，**不**把这两条做成 check 的不变量，**也不**为了验证而触发
一次付费重编译。

**理由**：

- **为什么改 prompt 而不进 check**：K3.7 划的界线是"能阻塞激活的规则必须无需判断即可
  裁定"。"页连得不够密"和"这句话像是自己补的"都是质量属性，不是机械不变量。把它们放进
  check 会让一次编译因为模型的表达风格而无法激活，而 check 的可信度恰恰来自它的确定性。
- **为什么不付费验证**：prompt version 升到 `wiki-prompt-3` 后，增量编译会**拒绝**跨
  prompt 版本复用页面，所以每个源的下一次编译必然在新规则下重写全部页面。也就是说，
  下一次因为自身原因发生的编译就是验证——专门花 200–400 秒的推理调用去验证一次
  prompt 措辞，是把钱花在确认文案上。
- **兜底已经在了**：lint 报孤立页，review 把无据断言标成 `unsupported`。两类问题都是
  **可见的**，不是静默存在于 wiki 里。

**改了什么**（`internal/knowledge/wiki_compile.go`，版本 `wiki-prompt-3`）：

- 新增"只用源文本出现过的词汇"：禁止引入源文档里没有的产品名、系统名、版本号、专有
  名词，**即使模型认为自己知道源文档在描述什么**。触发它的是真实缺陷——编译器把
  "Package 是 **AgentMate** 中知识库和 Skill 的基本组织单元"写进了 `wiki/package.md`，
  而 "AgentMate" 这个词在它的任何源文档里都不存在。
- 新增"入链要求"：每个页必须至少被另一个内容页指向，提到有独立页面的概念就必须链过去，
  并明确 index 页不算入链。触发它的是另一个真实缺陷——某个 build 里 13 个参与孤立判定的
  页有 8 个没有任何内容页指向它，尽管该 build 有 31 条非 index 链接。编译器在写页，
  但没在织网。

**推翻它需要什么**：新 prompt 编出来的 build 仍然孤立页成堆。那说明问题不在措辞而在
"一次调用产出整个 wiki"这个形式，届时该改的是编译的分解方式，不是继续加规则。

## 9. review 页数上限：保持上限，覆盖数字始终可见

**结论**：保持每个 build 最多审 20 页（`AGENTMATE_WIKI_REVIEW_MAX_PAGES`），按
citation 数降序，超限的 build 报 `partial` 而不是 `clean`。不做轮转覆盖。

**理由**：轮转（每次审上次没审的）看起来更公平，但它引入的状态解释不了自己——每个
build 是一套新的页面，上一个 build 的"审过哪些"对这一个 build 没有对应关系，跨 build
的轮转顺序因此是任意的。而 `partial` 与 `clean` 的区分已经保证了关键性质：**一次
被截断的 review 绝不会声称自己覆盖了没审的部分**。在"重要的页优先"和"每页都可能被审到
但覆盖率无法解释"之间，前者更诚实。

提高上限只是线性加钱，任何时候都可以调那个环境变量，不需要现在决定。

**推翻它需要什么**：出现"低 citation 页恰恰是错得最多的页"的证据。那时正确的做法是
改排序依据（比如按 review 历史上的 `unsupported` 率排），而不是提高上限或引入轮转。
