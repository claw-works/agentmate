# 待决策与待处理（需要产品/所有者输入）

这份文件只收"我不该自己替你定"的事。技术实现上的取舍我自己定并写进对应设计文档；
这里记的是需要你的判断、你的数据、或会花你的钱的事。

每条都标明：为什么它不能由我单方面决定、不决定的代价是什么、以及在哪里被引用。

## 1. 编译触发时机：同步后自动，还是显式触发

**为什么需要你定**：这条把成本与 raw 提交频率绑死。自动更符合"知识库保持更新"，
但每次 sync 都触发编译意味着一次 push 就是一次模型账单。

**不决定的代价**：现状是显式触发（`POST /api/knowledge/compile`）。知识库会静默变旧——
K3.7 的 `stale_citation` 现在能报出来了，所以代价至少是**可见的**，不再是无声的。

引用：K3 设计 §10 第 2 项。

## 2. 保留多少历史 build

**为什么需要你定**：build 是客户数据，淘汰策略是数据保留政策，不是技术参数。

**关键约束（我已经查过，供你判断）**：build 是回滚的依据，而 validation 信号有滞后性
（K3 §7.3），问题可能几周后才发现。**淘汰窗口不能短于信号显形周期**，否则会在发现问题时
恰好失去可回滚的目标。

**不决定的代价**：现状全部保留，持续增长。当前量级还很小（生产库个位数 build），不紧急。

引用：K3 设计 §10 第 3 项。

## 3. proposal 的处置人

**为什么需要你定**：proposal 不自动生效（K3 §7.5），那就必须有人批。"由谁批、在哪批、
多久不处理算过期"是流程设计，取决于你的团队怎么运作。

**不决定的代价**：K3.9 无法完成。生成 proposal 而没有处置路径，等于造一个只进不出的队列——
比不做更糟，因为它会让人以为反馈已经被处理了。

引用：K3 设计 §10 第 4 项。同时覆盖 query 回填与 memory 晋升候选。

## 4. 两家 provider 的实际单价

**为什么需要你定**：这是你的合同价格，我查不到也不该猜。

**为什么不填默认值**：编一个看起来合理的单价，会在成本账上放一个**看起来权威的错数字**。
`llm.Pricing` 现在默认 0，成本记账因此显示 0 而不是显示一个假的数。0 明显是"没配"，
一个编的数字不明显是错的。

**不决定的代价**：无法比较阿里云与 DeepSeek 的实际成本，也无法回答"增量编译省了多少钱"——
K3.4 的省钱效果目前只能用 token 数说，不能用金额说。

配置位置：`llm.Pricing{InputMicrosPer1KTokens, OutputMicrosPer1KTokens}`。

## 5. memory entry 大多没有 title

**为什么需要你定**：这是产品呈现问题。Context Pack 的 MEMORY 层条目现在只显示
`memory_type`，因为多数 entry 没有 title。要不要让写入方必填 title、还是自动摘要生成、
还是接受只显示类型——取决于你想让 agent 看到什么。

引用：`docs/skill-registry-next-actions.md:171`。

## 6. 三张表的 `account_id` 仍是 `SET NULL`

`api_logs`、`retrieval_queries`、`retrieval_feedback`。

**为什么需要你定**：删账户时，这三张表的行是保留（`SET NULL`，行留下但失去归属）
还是级联删除（`CASCADE`）。这是数据保留与租户删除语义的取舍，不是技术偏好——
牵涉"客户要求删除数据"时我们实际删了什么。

**不决定的代价**：现状 `SET NULL`，即账户删除后这些行变成无主数据留在库里。

引用：`docs/skill-registry-next-actions.md:119, 172`。

## 7. 【新增，K3.7 发现】编译器不把页连起来

**发现**：platform-registry 的激活 build 里，13 个参与孤立判定的页有 **8 个**没有任何
内容页指向它，尽管这个 build 有 31 条非 index 链接（详见 K3 设计 §17.6）。编译器在写页，
但没在织网。

**为什么需要你知情**：修法是改编译 prompt 强制交叉引用密度，**但要看到效果必须重新编译**，
而重编译花钱（一次全量约 200–400 秒的推理调用）。改 prompt 我可以做，花钱重编译三个 KB
应该你点头。

**另一个选项**：不改 prompt，而是把"交叉引用密度"做成 check 的新不变量——但那会**阻塞激活**，
而"页连得不够密"是质量问题不是不变量违反，按 K3.7 划的界线它不该进 check。所以我倾向
改 prompt。

## 8. 【新增，K3.8 发现】编译器把自己的世界知识写进了声称有出处的断言

**发现**：product-support 的 wiki 页 `wiki/package.md` 写着"Package 是 **AgentMate** 中
知识库和 Skill 的基本组织单元"，而 reviewer 指出 **"AgentMate" 这个词在任何源文档里都没
出现过**。这是编译器用自己的先验补了一句看起来有出处的话。

**为什么需要你知情**：这类问题的修法是改编译 prompt（更严格地要求"只写原文支持的内容"），
但**要看到效果必须重新编译**，而重编译花钱。与第 7 项是同一个决定的两面：都要重编译才能验证。

**已有的兜底**：review 现在会把这类断言标成 `unsupported`，所以它至少是**可见的**，
不再静默存在于 wiki 里。

## 9. 【新增，K3.8 发现】review 页数上限与覆盖策略

**现状**：review 默认每个 build 最多审 20 页（`AGENTMATE_WIKI_REVIEW_MAX_PAGES`），
按 citation 数从多到少排。超过上限的 build 得到 `partial` 而不是 `clean`。

**为什么可能需要你定**：大知识库上 citation 少的页会**永远排不到**。要不要
（a）提高上限——线性增加成本；（b）轮转覆盖（每次审上次没审的）——需要额外记录状态；
（c）就这样，接受"重要的页优先"。

我倾向 (c) 加上"覆盖数字始终可见"，因为它不引入新状态，而 (b) 会让"某一页的判定"依赖于
历史轮转顺序，难以解释。但这条会花你的钱，所以列在这里。
